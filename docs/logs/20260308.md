# 2026-03-08 工作记录

## 今天主要在做什么
今天主要推进的是 duplicate deps 的治理口径收口。

如果用一句话概括，这件事是在解决“质量门禁已经有了，但 duplicate deps 这一项的衡量方式还不够准确”，目的是让后续继续做后端工作时，门禁既能拦住新增债务，也不会因为统计口径过粗而反复误报。

## 为什么今天先做这件事
当前项目正处于后端先行、UI 暂缓接入的阶段，所以今天优先处理 duplicate deps，而不是直接进入新的 UI 或业务迁移。

这样安排的原因是：
- `P6-1` 的统一质量门禁虽然已经落地，但 duplicate deps 之前还是“看到重复就失败”的粗口径。
- 这会把很多来自 `tauri` / `image` / `windows` 生态的历史分叉，和真正新增的依赖分叉混在一起。
- 如果不先把治理口径固定，后面继续推进 `P6-2` 时，质量门禁会变成噪音，而不是可依赖的判断依据。

## 今天推进了哪些关键点

### 1. 把 duplicate deps 从绝对归零改成 baseline-delta
今天先处理了 `scripts/quality/check-duplicate-deps.ps1`。

这件事本身做了什么：脚本不再只统计 `cargo tree -d` 的原始 header 数，而是开始区分真正的多版本 crate family，以及仅在不同 host/target/build 场景重复出现的同版本 package header；同时引入 `config/quality/duplicate-deps-baseline.json` 作为正式基线。

它的重要性在于：`P2` 本来就应该按 delta 治理，而不是强行要求初始化阶段一次性清零所有生态依赖分叉。

它对后续的帮助是：后面只要新增了新的 duplicate family，或者给已有 family 又引入了新版本，门禁就会立即失败；如果没有新增，门禁就允许在当前基线上继续推进其他工作。

### 2. 把原来的 63 项噪音指标先收口成 23 个真实 family
今天还推进了 duplicate deps 基线记录的整理。

这一步解决的是：之前 summary 里的 `63` 实际上是原始 header 数，里面混有同版本重复 header，不能直接当成真正的多版本依赖债务总量。

它说明目前项目已经从“只会报一个大数字”进入到了“能分清真实多版本 family 与统计噪音”的阶段。

### 3. 用完整 gate run 验证新的治理口径
另外补上了完整的质量门禁复跑。

这件事虽然看起来不大，但它的意义是：不是只单独跑了 duplicate deps 脚本，而是重新执行了整套 `npm run check:quality`，确认新的 duplicate deps 口径已经能和原有 `fmt / clippy / nextest / coverage / deny / audit / udeps / forbidden edges / tauri build` 一起工作。

## 今天遇到的问题

### 1. 基线文件最初用了非 ASCII 文本
今天遇到的问题是：基线 JSON 最初写了中文说明，而 PowerShell 5 在默认读取编码下把它读坏了，导致 `ConvertFrom-Json` 解析失败。

它带来的影响是：duplicate deps 脚本第一次运行直接失败，门禁还没来得及比较基线就中断了。

最后的处理方式是：把基线文件里的说明文字改成 ASCII，避免编码差异再次影响 JSON 解析。

这件事说明后续需要特别注意：PowerShell 5 下的配置文件尽量保持 ASCII，尤其是 JSON 这种需要稳定反序列化的文件。

### 9. 再给 DB upgrade 补最小守卫
继续推进 `P6-2` 时，今天还补了一轮数据库 schema 异常防线。

这件事本身做了什么：`crates/media-db/src/migrations.rs` 现在会在打开数据库时先拦住“schema version 比当前仓库还新”的情况，并在迁移完成后校验当前 version 对应的关键表是否真的存在；同时测试里补了两类异常：伪装成最新版本但缺少必需表，以及未来 schema version。

它的重要性在于：如果没有这一层，损坏 fixture 只要把 `user_version` 改大，就可能绕过迁移，等到更后面的 repository 代码才以更模糊的方式失败。

它对后续的帮助是：现在 DB upgrade 的坏路径已经不只是“不是 sqlite 会失败”，而是开始覆盖“版本号和真实结构不一致”的情况，这对后续补 replay / upgrade 样本是更接近真实问题的基础。

### 10. 再补一类 replay 级别的列漂移异常
继续往下补时，今天又把 DB replay 场景往前推进了一点。

这件事本身做了什么：新增了 `crates/media-db/tests/fixtures/schema_v1_missing_exists_flag_fixture.sql`，故意模拟“旧版本 fixture 还看起来像 v1，但核心列已经丢失”的情况；同时把 migration 校验从“只看表是否存在”扩展到“关键列也必须存在”。

它的重要性在于：这比单纯缺表更接近真实 replay 问题。真实世界里更常见的是 fixture 被手改、列被漏掉，或者快照和 schema 文档不同步，而不是整张表完全消失。

它对后续的帮助是：现在 DB 异常路径已经开始覆盖文件损坏、版本漂移、缺表和缺列四层问题。后面如果继续补 replay/upgrade 样本，就可以更聚焦在哪些列/索引/约束是真正需要被守住的，而不是先从最粗粒度的坏文件场景重新开始。

### 11. 再补一类 replay 级别的索引漂移异常

这件事本身做了什么：新增了 `crates/media-db/tests/fixtures/schema_v2_missing_archive_entry_index_fixture.sql`，专门模拟“表和列都还在，但 archive entry 的关键唯一索引已经丢失”的情况；同时 migration 校验开始要求 `idx_sources_library_path`、`idx_media_assets_source_ref`、`idx_archives_source_id`、`idx_archive_entries_archive_path`、`idx_thumbnails_asset_id` 这些关键索引必须存在。

它的重要性在于：索引漂移比缺表更隐蔽。系统可能还能跑，但唯一性约束、查询语义和后续性能都已经开始偏离，最容易变成后面才发现的“慢性问题”。

它对后续的帮助是：现在 DB replay / upgrade 的坏路径已经从文件、版本、表、列进一步扩到了索引层。后面如果还要继续补约束或 foreign key 类异常，就已经有了一条比较完整的守卫链。

### 12. 再把 foreign key 约束也提前锁死
继续往下补时，今天把 DB 约束类异常也一起补上了。

这件事本身做了什么：`MediaDatabase::open(...)` 现在会主动启用 SQLite 的 `foreign_keys`；同时 migration 校验开始要求 `sources.library_id -> libraries.id`、`archives.source_id -> sources.id`、`archive_entries.archive_id -> archives.id`、`thumbnails.asset_id -> media_assets.id` 这些关键 foreign key 必须存在；另外还补了 `crates/media-db/tests/fixtures/schema_v2_missing_thumbnail_foreign_key_fixture.sql`，模拟 v2 replay fixture 缺少 `thumbnails.asset_id` 外键的情况。

它的重要性在于：foreign key 漂移比索引漂移更容易演变成“表面一切正常，但引用关系已经悄悄失真”的问题。等业务层真的读到脏引用时，排查成本会更高。

它对后续的帮助是：现在 DB replay / upgrade 的守卫链已经覆盖文件、版本、表、列、索引和 foreign key 六层。后面如果还要继续往下补，最自然的方向就只剩更细的 constraint 语义或 command 层错误收口，而不是继续回到 schema 基础守卫。

### 13. 再把已落盘脏数据也提前拦住

它对后续的帮助是：现在 DB replay / upgrade 的守卫已经从结构完整性继续扩到了数据完整性。后面如果还要继续推进 `P6-2`，最自然的方向就更偏 command 层错误统一，而不是继续在 DB 基础结构上做同类补丁。
