# 2026-03-11 工作记录

## 今天主要在做什么
今天主要推进的是：把项目的 UI 路线从“等旧仓 theme 收口后再整体迁移”，正式改成“布局先行、样式链重建、面板内容分步接回”的新实施方式，并把这条新路线真正落成文档结构和第一批界面骨架。

如果用一句话概括，这件事是在解决“旧仓 UI 主题系统推进不顺，导致新仓 UI 迟迟无法开始”的问题，目的是让项目不再被旧 theme 收口节奏卡住，而是可以在新仓里按切片逐步建立自己的初始 UI 架构。

## 为什么今天先做这件事
当前项目已经不是“只有后端骨架”的状态，`I1` 的 repository / adapter 接线也已经有了首轮结果，所以今天优先处理的是 UI 路线切换和 `U0` 壳层落地，而不是继续写新的后端能力。

这样安排的原因是：
- 旧仓真正卡住的部分已经不是交互关系，而是 theme 系统和样式链条本身；如果继续等待，整个新仓 UI 会长期停在说明阶段。
- 新仓后端边界、repository 壳层和宿主协议已经足够稳定，已经具备“先搭新壳层，再逐步接面板”的条件。
- 只有先把文档、定义边界和 `U0` 的四容器骨架固定下来，后面 `U1/U2/U3` 才能按切片验收，而不是每次又回到“先等旧 UI 完整收口”的老问题上。

## 今天推进了哪些关键点

### 1. 正式把 UI 路线从“等待迁移”改成“分步重建”
今天先处理了项目层面的路线判断，而不是直接改页面样式。

这件事本身做了什么：先结合当前仓库状态重新判断，确认后端地基、`I1` 壳层和 repository 边界已经足够支撑 UI 前置；然后把原来“等旧 App theme 收口后再迁移”的思路，改成“先迁布局骨架、再重建样式链、再逐面板接内容”的新路线。

它的重要性在于：这一步不是简单改优先级，而是把项目从“被旧仓状态牵着走”推进到“新仓按自己的节奏建立 UI 架构”。

它对后续的帮助是：从现在开始，UI 工作可以像后端阶段一样拆成 `U0/U1/U2...` 这种可分段验收的切片，不需要再等一个“大一统 theme 系统”完全收完才开工。

它对后续的帮助是：后面每推进一个 UI 切片，都可以沿用今天这个模式——先写定义，再做实现，再跑最小验证，而不是页面改了很多、文档却还停在旧状态。

## 今天遇到的问题

### 1. U0 第一轮落地后，打开应用看到的是“说明”，不是“真正的布局占位”
今天遇到的问题是：虽然 `U0` 已经把背景层和四大容器骨架做出来了，但当前各容器里的内容仍然偏“说明性文字”和开发期验证信息，看起来更像阶段说明页，而不是正式的初始界面。

它带来的影响是：从实现角度看，这一轮确实验证了容器分隔和样式变量；但从使用者直觉看，打开应用后会觉得“这不是布局，而是在解释布局”。

最后的处理方式是：先确认这属于 `U0` 首轮验证的正常结果，不是样式接错；同时也明确这不应作为长期默认界面。下一步进入 `U0` 收口或 `U1` 前，应该把这些长说明收敛成更轻的占位块、空态和标题结构。

这件事说明后续需要特别注意：开发期验证内容可以暂时存在，但不能长期占据主界面，否则项目会从“搭骨架”滑向“把说明页当产品壳”。

### 2. 需要澄清 Tauri 开发态的重启规则，避免把正常热更新误当成异常
今天还发现一个容易让后续操作变笨重的问题：并不是每次改完代码都需要重新执行 `npm run tauri:dev`。

目前的结论是：如果只是前端 React/CSS 改动，开发态通常会通过 Vite 热更新直接生效；只有在宿主配置、依赖、环境或 Tauri/Rust 层出现变化时，才更可能需要重启开发进程。这件事虽然不是业务功能，但会直接影响后续 UI 迭代效率。
