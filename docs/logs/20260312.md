## 这次具体改了什么

### 1. 把“清除数据库”改成两段式流程

这次先把设置页里的 `清除数据库` 按钮改成只负责打开确认面板，不再直接进入后端清理动作。

新的行为是：

- 第一次点击 `清除数据库`
  - 只打开确认小面板
  - 不执行任何清理
- 点击 `取消`
  - 只关闭小面板
  - 当前数据库与路径状态保持不变
- 点击 `确认清除`
  - 才真正调用 `repository.database.clear()`
  - 成功后再 reload

这样修完后，确认流的副作用边界就明确了：打开确认 UI 不等于已经执行。

这样做的意义不是只为了“看起来统一”，而是让确认行为重新回到当前 UI 定义内部，避免系统弹窗和应用内样式链分裂。

## 补充更新：已处理一次 Rust/Tauri 构建链路的真实阻塞故障

### 8. `link.exe` 的 `LNK1318` 不是单点故障，实际前因是 PDB 压力叠加磁盘空间耗尽
这次在继续验证 Tauri/Rust 宿主构建时，出现了 `link.exe` 失败并抛出 `LNK1318` 的错误。单看报错表面是 `PDB` 写入异常，但进一步排查后确认这不是单一“链接器偶发坏掉”，而是两个因素叠在一起：一是 dev 构建的调试信息体量已经比较大，二是工作盘 `Z:` 当时已经被 `target` 目录打满到 `FreeGB : 0`，导致链接阶段写 `mediaplayernext.pdb` 时直接触发 `LIMIT (12)` 与后续一串 `os error 112`。

这件事本身做了什么：先在工作区根 `Cargo.toml` 里补了 `[profile.dev] debug = 1`，把 dev 构建的调试信息压力往下压一档；随后执行了 `scripts/run-cargo-with-msvc.cmd clean --manifest-path Z:\Playground\CurrentWorking\MediaPlayerNext\src-tauri\Cargo.toml`，一次性清掉了约 `30.9 GiB` 的 Rust 构建产物。清理后重新检查，`Z:` 盘可用空间从 `0 GB` 恢复到约 `33.13 GB`。在这个基础上再重新跑宿主构建，`mediaplayernext` 已经重新成功编译通过。

它的重要性在于：这次已经确认，当前仓库的 Rust/Tauri 构建阻塞并不一定是代码逻辑问题，可能是 `target` 目录体积与 Windows `PDB` 写入限制共同导致的工程级故障。后续再看到类似 `LNK1318`，不能只盯着 linker 本身，而要先一起检查磁盘余量和 `target` 体积。

### 9. 当前仓库对这类构建阻塞的处理方式已经明确
这次也顺便把处理口径固定下来了。

- 第一优先：先检查工作盘剩余空间，尤其是 `Z:\Playground\CurrentWorking\MediaPlayerNext\target`
- 第二优先：必要时执行 `scripts/run-cargo-with-msvc.cmd clean --manifest-path Z:\Playground\CurrentWorking\MediaPlayerNext\src-tauri\Cargo.toml` 回收空间
- 第三优先：保留当前 `Cargo.toml` 里的 `[profile.dev] debug = 1`，避免 dev 下生成过重的调试信息

这样做的意义是：以后再遇到 `PDB` / `link.exe` / `LNK1318` 一类问题时，处理路径已经不再模糊，可以直接按“检查空间 -> 清理 target -> 重试构建”的顺序排查，而不是先怀疑新接入的功能代码本身坏掉。
