# 2026-03-12 工作记录

## 今天主要修了什么

今天先修的是 `设置 -> 数据库管理 -> 清除数据库` 的确认流问题。

用户反馈的两个点是成立的：

- 清除动作不应该和确认弹窗耦合在原生 `confirm` 里
- 最终确认不该走系统原生弹窗，而应该回到新仓已经固定的 `4 小面板层`

## 这次具体改了什么

### 1. 把“清除数据库”改成两段式流程

这次先把设置页里的 `清除数据库` 按钮改成只负责打开确认面板，不再直接进入后端清理动作。

新的行为是：

- 第一次点击 `清除数据库`
  - 只打开确认小面板
  - 不执行任何清理
- 点击 `取消`
  - 只关闭小面板
  - 当前数据库与路径状态保持不变
- 点击 `确认清除`
  - 才真正调用 `repository.database.clear()`
  - 成功后再 reload

这样修完后，确认流的副作用边界就明确了：打开确认 UI 不等于已经执行。

### 2. 最终确认改走 4 小面板层

这次没有继续使用原生 `window.confirm`，而是直接在桌面前端里补了一个确认小面板，样式走现有的 `4 小面板层` 骨架：

- 使用 `.mpx-dialog-panel`
- 按钮继续走 `5.1 通用变体`
- 内容只保留确认标题、清理范围说明、取消/确认两个动作

这样做的意义不是只为了“看起来统一”，而是让确认行为重新回到当前 UI 定义内部，避免系统弹窗和应用内样式链分裂。

### 3. 补了关闭与执行态约束

这次还顺手把确认小面板的最小交互边界补齐了：

- 支持 `Escape` 关闭
- 点击遮罩关闭时，只关闭小面板，不关闭外层设置面板
- 清除执行中会禁用取消/确认按钮，避免重复触发
- 如果清除失败，错误会留在小面板内显示，而不是静默吞掉

## 这次修改影响到什么判断

- 已经确认：数据库清除这类高风险动作，最终确认必须回到 `4 小面板层`
- 已经确认：设置页中的动作按钮不应把“打开确认 UI”和“执行不可逆动作”写在同一个点击入口里
- 已经确认：`4 小面板层` 不只是样式占位，而是已经开始承接真实业务确认流
