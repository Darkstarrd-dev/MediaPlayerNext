# 2026-03-06 工作记录

今天做的事情，如果用最简单的话来说，就像是在给一座还没正式搬进去的新房子打地基、装水电、挂门牌，还顺便把以后怎么搬家这件事认真商量清楚了。这个新房子就是 `C:\opencode\MediaPlayerNext`，它不是老房子 `C:\opencode\MediaPlayer` 的直接复制品，而是为未来迁移准备的一块新工地。今天我们没有把旧房子里的家具一股脑搬过来，而是先讨论“为什么要搬、哪些东西值得搬、先搬什么、后搬什么、哪些东西先别动”，然后再真正动手把新房子的基础设施搭起来。

一开始，我们先花了很多时间讨论“迁移到 Rust 到底值不值”。这个问题表面看像是在问语言选择，实际上是在问：我们到底想解决什么问题。因为如果连问题都没想清楚，就像医生还没诊断清楚就乱开药，最后很容易治错地方。我们把整个老项目分成了很多部分，一块一块去看：前端界面、数据库、资源入库、解压查看、缩略图、预加载、播放器、音乐可视化、字幕生成、外部 AI 接口，还有以后可能做的小型快速查看器。这样拆开后，事情就清楚很多，不再是“整个项目要不要迁”这么吓人的大问题，而是“每一块东西适不适合迁、迁了有什么好处、代价是什么”。

关于前端，我们讨论出了一个很重要的结论：如果未来迁到 Rust，前端最好继续保留 `Vite + React + three.js` 这套架构，不要一开始就去碰纯 Rust UI。这个判断不是因为 Rust UI 不厉害，而是因为现在老项目的前端已经发展出了一整套自己的界面结构和 theme 系统，而且还带着音乐可视化、three.js 或 WebGL 这类偏浏览器生态的能力。保留前端不动，有两个特别现实的好处。第一，现有界面、主题系统和渲染层不用全部重写；第二，前端仍然能继续享受 tree shaking、代码分割、Vite 的开发体验这些优点。我们还特别明确了一点：如果只是把 Electron 的壳换成 Rust 壳，确实能在体积、空闲内存、启动速度上得到明显收益，但界面渲染速度不会神奇地一下子快很多，因为画页面的方式还是 WebView，React 和浏览器布局这套机制并没有本质变化。换句话说，这更像是把原来比较重的背包换成轻一点的背包，人走路会轻快一些，但腿本身没有突然长长一截。

接着我们把注意力放到后端最辛苦的部分，也就是重 I/O。你可以把这部分想成仓库管理员在不停搬箱子、拆箱子、给箱子贴标签、提前把下一箱要看的东西放到手边。这里包含了几个核心场景：资源入库，也就是扫描目录、识别文件、写入索引；查看时解压，也就是打开压缩包里的一张张图片；缩略图生成，也就是提前做小图缓存；看图预加载，也就是你正看第十张的时候，后台悄悄准备第十一张、第十二张。我们讨论后几乎是一致确认：这部分是最值得迁到 Rust 的。因为这些工作很依赖本地文件系统、并发调度、缓存和较低开销的原生处理，Rust 正好擅长这些事情。它不会像 Node/Electron 那样很容易堆出很多 Buffer、对象和跨线程调度成本，也更适合把扫描、读取、转换、写库这些步骤紧密地串在一起。

说到缩略图，我们专门停下来认真想了很久。因为现在老项目是基于 `sharp` 的，而 `sharp` 背后其实已经站在一个很强的图像处理基础上了。也就是说，如果有人说“只要换成 Rust，缩略图一定大幅更快”，这句话是不严谨的。真正更合理的说法应该是：Rust 能让整条缩略图流水线更顺，减少中间搬运、减少不必要的调度和复制，但并不代表换一个 Rust 库之后，图像缩放算法本身就一定碾压 `sharp`。我们还顺便讨论了 GPU 方案，结论也很清楚：Rust 当然可以做 GPU 加速图像处理，但现阶段并没有一个像 `sharp` 那样成熟、易用、适合直接生产替换的 Rust GPU 缩略图库。所以如果未来真要迁，最务实的路线不是“为了 GPU 而 GPU”，而是先把 CPU 路线和整条处理链条做扎实。

数据库这部分，我们的讨论也比较务实。重点不是去追求某个听起来更高级的新数据库，而是先看当前项目到底适不适合继续用 SQLite。结果很明确：适合，而且很适合。老项目现在本来就是本地媒体库场景，SQLite 的定位和它很匹配。Rust 版 SQLite 会更适合和扫描、缓存、入库这些本地流程整合在一起，尤其在批量写入和事务控制上会更舒服，但这不代表只要语言一换，数据库就立刻像火箭一样起飞。我们达成的判断是：未来值得做的是“Rust + SQLite + 重 I/O 原生化”，而不是“为了追新而换别的数据库”。这个判断很重要，因为它避免了后面跑偏。

播放器部分我们拆成了两层来看。基础模式那层，现在相当依赖 Electron 里自带的浏览器媒体解码能力。如果未来换到 Rust 桌面壳，比如 Tauri，那基础媒体播放仍然可以走 WebView 的能力，所以这一层并不是没路走。区别在于，原来依赖的是 Electron 自带 Chromium，现在更接近依赖系统 WebView。这样做的好处是能去掉 Electron 的大壳子，但也会带来平台间编解码行为更依赖系统环境的问题。高级模式就不一样了，原来就依赖 `mpv + ffmpeg` 这些独立二进制工具。我们讨论后认为，这部分未来最好的做法其实不是重写这些成熟工具，而是继续沿用它们，把控制层从 Node/Electron 迁到 Rust。这样就像保留一台已经很可靠的大机器，只把旁边负责调度和指挥它的控制台换成更稳定的版本。

音乐模式里的 shader 可视化，是今天讨论里最有“技术味道”的部分之一。因为这块不是普通按钮和列表，而是跟 `GLSL`、`Shadertoy`、`WebGL2` 这些图形能力绑得很深。我们一起仔细分析后，得出的判断是：理论上当然可以迁到 Rust 原生图形栈，比如 `wgpu`，但成本很高，而且不一定能完整保留现有 GLSL/Shadertoy 的兼容体验。更重要的是，即使迁过去，性能也不一定会有压倒性的提升。因为如果瓶颈本来就在 shader 自身太重或者 GPU 本身吃满，那换语言并不会像施魔法一样解决所有问题。所以最后我们把这块列为了“未来尽量保留前端图形路线，不作为第一批 Rust 迁移目标”的内容。这个决定其实很成熟，因为它承认了现实世界里“不是所有技术上能做的事，都值得第一时间做”。

字幕生成则是另一种完全不同的难点。它不像前端那样主要是界面层，也不像数据库那样主要是本地存储，而是 `Node worker/process + sherpa-onnx-node + VAD + 说话人处理 + 持久化` 这一整条很复杂的 AI 推理和会话处理链。我们专门讨论了 Rust 有没有等价方案，也承认从理论上说当然有，但工程风险很高，尤其是行为一致性、provider、模型调用和长期维护这些方面。因此最后形成了一个非常重要的决定：新的 Rust 架构里，字幕生成先不强迁，继续保留 Node.js sidecar。这不是“偷懒”，恰恰相反，这是把最难、最脆弱、最容易拖慢整个迁移节奏的一块，放到最后甚至长期独立出来处理。这样就能让其他更值得迁、收益更直接的部分先落地。

外部 AI 接口调用这部分，我们也聊得比较彻底。这里的判断反而轻松一些，因为这类能力本质上大多是 HTTP、SSE、WebSocket、鉴权、重试、超时控制这些网络请求能力。Rust 完全能接住，而且很多时候还会更稳。所以这部分我们认为未来是可以较轻松迁到 Rust 的，没必要为了它专门保留 Node。

之后我们进一步讨论了开发路线应该怎么安排。一个很关键的问题是：到底应该先迁，还是先等老项目的前端 theme 系统彻底收束好再迁。这个问题像是在问，是不是应该一边搬家一边还继续拆旧家的墙。最后我们的答案非常明确：先别急着搬，先让旧家的前端收束完成，尤其是 theme 系统和 UI 边界。因为如果现在就一边整理主题系统一边开始跨技术栈迁移，问题会纠缠在一起，到时候很难知道一个 bug 究竟来自旧系统还没收束，还是来自新壳层、桥接层或者新运行时。先把老项目的前端边界稳定下来，再开始迁移，成功率会高很多，回归范围也更可控。这就像先把旧家的东西整理打包编号，再搬去新家，会比一边收拾一边乱装车可靠得多。

然后我们又把目光看向了未来更远一点的可能性，比如 Rust 是否有等价于 three.js 的框架，Rust 原生 UI 是否能保留类似 HTML+CSS 的灵活性，Windows 平台上的 Rust 工具链是否成熟，以及如果只做一个极快、极小的看图器，是不是 C++ 更合适。这里最后形成的世界观其实很清晰：如果你要的是完整项目的长期演化，保留 Web 前端、用 Rust 做重 I/O 和桌面宿主，是最平衡的路；如果你要的是一个启动极快、占用极小、像系统查看器一样的超轻工具，那条线还是更适合 C++ + Win32 API。也正因为如此，我们顺势想出了一个非常有意思的双轨设想：未来可以有一个极轻的快速查看器，用 C++ 实现，负责秒开图片；再有一个完整的大型管理器，用 Rust 做核心，负责媒体库、缩略图、归档、播放器等复杂能力。小工具还能把当前查看的内容推送给完整版。这个想法不是今天就要实现，但把它说清楚很重要，因为它帮助我们明白“不是所有需求都要硬塞到一个程序里”。

在路线基本商量清楚后，今天就进入真正动手的阶段了。首先，我们决定不用把 Rust 初始化直接塞进老项目，而是单独在 `C:\opencode\MediaPlayerNext` 建一个全新的仓库。这样做的原因非常现实：老项目还在继续演化，尤其 theme 系统还没完全收束，如果现在把探索性的 Rust/Tauri 工作直接塞进去，构建链路、依赖、文档、CI 和目录结构都会混在一起。新建一个仓库，就像在隔壁搭一个实验工地，既不会打扰原来的住户，也方便我们自由试错。这个决定其实影响很大，因为它意味着我们后面可以放心地调目录结构、依赖和脚本，而不用担心破坏旧仓主线。

新仓的结构，我们也不是随便摆的。今天定下来的形状是：`apps/desktop` 放 React 前端，`apps/subtitle-sidecar` 放 Node.js 字幕 sidecar，`src-tauri` 放 Tauri 宿主和 Rust 入口，`packages/contracts` 预留给未来共享协议，另外还有 `docs`、`config`、`scripts` 等辅助目录。为什么这样拆？因为我们不想把所有东西都揉成一坨。React 前端和 Rust 后端虽然属于同一个产品，但它们的开发节奏、依赖和构建方式不一样；而字幕 sidecar 未来本来就准备保留 Node，那它单独放在一个 workspace 里会更清楚。今天做的初始化，本质上就是先搭好这些盒子，让以后每类东西都有自己的位置。

真正开始安装依赖和搭脚手架时，遇到的第一个大麻烦，是 Rust 工具链的安装。最开始看起来像是没装上：在当前环境里用常见方式检查时，找不到 `rustup`。但你随后在 `cmd` 环境下给出了关键信息，说明 `rustup` 实际已经在 `C:\Users\Houpy\.cargo\bin\rustup.exe`，只是当前 shell 没把这件事表达清楚。这一步非常关键，因为它提醒我们，问题不一定是“东西没装”，也可能是“环境没有正确看到它”。然后我继续去装 Rust stable toolchain，结果又卡住了联网下载阶段，报的是连接被拒绝。后来才确认，问题的根子不在 Rust，也不在工具链本身，而是代理端口用错了。我最开始沿用了旧环境里提到过的 `2080` 端口，但你指出正确端口应该是 `3066`。等把 `HTTP_PROXY` 和 `HTTPS_PROXY` 都改成 `http://127.0.0.1:3066` 之后，Rust stable toolchain 就顺利下载安装好了。这一步像是在找迷路的电线，前面一直觉得机器不工作，其实是电源插在了错误的插座上。

接下来，我在新仓下创建了基本目录，初始化了 Git 仓库，然后用 Vite 脚手架创建了 `apps/desktop`。这里也出现了一个小插曲：第一次用绝对路径直接调用 `create-vite` 时，路径被拼成了重复的形式，导致脚手架试图在 `C:\opencode\MediaPlayerNext\C:\opencode\MediaPlayerNext\apps\desktop` 这种根本不存在的地方创建项目。这个问题的原因很简单，是工具在当前工作目录里又重复追加了一遍绝对路径。所以我改用相对路径 `apps/desktop` 再执行一次，脚手架就正常工作了。这个小问题虽然不大，但也再次提醒，Windows 环境下绝对路径和当前工作目录混用时要特别小心。

随后开始初始化 Tauri 宿主。但这里第二个大问题出现了：联网安装 `@tauri-apps/cli` 时，默认 npm 请求没有走正确代理，于是超时了。我通过为安装命令显式加上 `HTTP_PROXY=http://127.0.0.1:3066 HTTPS_PROXY=http://127.0.0.1:3066` 解决了这个问题。也就是说，今天不仅 Rust 工具链需要知道正确的代理，npm 也需要，不然它就会像不知道往哪条路走的快递员一样，一直在外面兜圈子送不到。

Tauri 宿主目录 `src-tauri` 搭好后，我又补了一整套基础文件：`Cargo.toml`、`build.rs`、`tauri.conf.json`、Rust 入口、运行时自检代码，还有一个 `runtime-smoke-check` 二进制。这个自检小程序很重要，因为我们现在的目标并不是开始迁移业务，而是确认未来迁移必须依赖的几个关键运行时已经能够在新仓里被正常调用。于是我在 Rust 侧写了非常简单但很关键的检查逻辑：用 `rusqlite` 打开内存数据库并读取 SQLite 版本，再调用配置文件里写好的绝对路径去运行 `ffmpeg -version` 和 `mpv --version`，把第一行结果打印出来。这种 smoke check 就像装新厨房时先确认水龙头出水、煤气点火、电灯能亮，先证明最基础的设施是通的。

与此同时，我在 `apps/subtitle-sidecar` 里只做了一个很克制的 Node.js sidecar 骨架：加了 `sharp`、`zod`、`typescript`、`tsx` 这些必要依赖，然后写了一个小小的检查脚本，用 `sharp` 生成一张 2x2 的 PNG 图片，确认 `sharp` 在新仓环境里真的能跑。这里刻意没有迁移任何真实字幕逻辑，因为我们前面已经明确决定，这个阶段只做基础准备，不碰真正的业务迁移。字幕 sidecar 现在更像一间已经装好电源和桌子的空房间，真正的大机器以后再搬进去。

做这些脚手架的时候，还专门保存了一个很重要的配置文件：`C:\opencode\MediaPlayerNext\config\local.paths.json`。这里面写了几个本地运行时和参考资源的绝对路径，比如 `ffmpeg`、`ffprobe`、`mpv`，以及旧仓的位置。为什么非要做这个文件？因为未来迁移过程中，外部二进制和旧仓参考路径很可能会频繁用到。把它们集中记录下来，能避免脚本里到处写死路径，也让代理开发时知道“这几个东西是本地真实依赖，不是随便猜的”。

然后出现了今天第三类问题：Windows 下 Rust 依赖里有一些需要真正调用 MSVC 编译工具链的部分，例如 `rusqlite` 走 bundled SQLite 的时候，会在本地编译 SQLite C 代码。一开始直接跑 `cargo check`，报错里能看到找不到正确的头文件路径，比如 `stdarg.h` 所在路径集没有准备好。这说明虽然系统里有 `cl.exe`，但没有在正确的开发者命令环境中运行。这里我没有去手工塞一大堆环境变量，因为那样既脆弱又难维护，而是做了更稳妥的方案：在 `scripts` 目录里创建了几个 Windows 批处理脚本，先调用 Visual Studio 的 `VsDevCmd.bat`，把完整的 MSVC 编译环境准备好，再运行 `cargo`、`tauri dev`、`tauri build`。这种做法的好处是以后每次开发都走同一条路，避免今天能编、明天不能编的环境漂移问题。简单说，就是先穿好安全服再进工地，而不是一边施工一边现找头盔。

再往后又碰到第四个问题：Tauri 在构建时要求有图标文件，而当时仓库里没有 `icon.ico`。另外，因为我们定义了两个 Rust 二进制目标，一个是主程序 `mediaplayernext`，一个是 `runtime-smoke-check`，所以 `cargo run` 也不知道默认该跑哪一个。于是我先用 PowerShell 生成了一个很简单的 PNG 图标，再借助 `ffmpeg` 缩放和转换，做出 Tauri 需要的 `icon.ico` 和几张 PNG 资源。然后在 `Cargo.toml` 里设置 `default-run = "mediaplayernext"`，告诉 Cargo：正常开发启动时请跑主程序，不要发呆。这两个动作，一个补的是门牌，一个补的是路线图，没有它们，后面启动过程就会卡壳。

做完这些基础设施后，我开始进行真正的验证。首先跑的是 `npm install`，确认整个 workspace 的 npm 依赖都能装好。然后跑 `cargo check`，这一步会把 Rust/Tauri 相关依赖全部解析和编译一遍，确认宿主工程结构没有破损。接着跑 `npm run check`，它会顺次验证 Node sidecar 的 `sharp` 和 Rust 宿主侧的 `rusqlite + ffmpeg + mpv`。这一套跑通后，我们得到了几条非常实在的结果：`sharp` 能生成图片，`sqlite_version` 能读出来，`ffmpeg` 能返回版本信息，`mpv` 也能通过绝对路径正常调用。对一个还没开始迁移业务的新仓来说，这已经是一套很扎实的“体检通过”证明了。

之后我继续检查前端和 Tauri 的联动。`npm run build:web` 成功构建出默认 React 页面，说明 `apps/desktop` 的脚手架和 workspace 没问题。然后用 `npm run tauri:dev` 去实际拉起开发环境。一开始它失败了，因为 Tauri CLI 在当前环境中找不到 `cargo metadata`，根本原因是虽然 Rust 已装好，但 `PATH` 里没有包含 `C:\Users\Houpy\.cargo\bin`。于是我把这一路径显式加入到了几个批处理包装脚本里，让它们在调用 Tauri 和 Cargo 前先把这条路放进 PATH。再试一次后，Vite 开发服务器成功启动，Tauri 主进程也成功编译并运行，只是因为命令执行超过了 CLI 的超时时间而被工具中止展示，并不是应用本身没起来。这一步很像汽车已经点火开动了，只是我们在旁边拿着秒表的人先把表停了。

后来你又注意到一个很实际的问题：为什么这个还没迁什么代码的新项目，光初始化就占了将近 4GB。于是我没有凭感觉回答，而是老老实实去测目录大小。结果一下子很清楚：几乎所有体积都在 `C:\opencode\MediaPlayerNext\src-tauri\target`，而不在源码目录，不在 `node_modules`，也不在文档。再往下看大文件列表，就发现有一个巨大的 `mediaplayernext_lib.lib`，还有很多 `.rlib` 和 `.pdb` 调试符号文件。这里的问题不在于“项目写多了”，而在于当前 `Cargo.toml` 为库配置了 `staticlib + cdylib + rlib` 三种 crate type，而我们当前阶段实际上根本不需要前两种。它们在桌面初始化阶段只会制造额外大体积和更重的链接负担。

于是，今天最后一个实打实的优化动作，就是把 `C:\opencode\MediaPlayerNext\src-tauri\Cargo.toml` 里的 `crate-type` 改成只保留 `rlib`。改完之后，我没有只停在“理论上应该变小”这个层面，而是立刻执行了清理：先 `cargo clean` 删除旧的 `target` 目录，再重新跑一遍 `npm run check` 让它按新配置重建，然后重新测量大小。结果从大约 `4100 MB` 降到了 `2295 MB`，直接少掉了差不多 `1.8 GB`。这说明我们不是靠猜，而是通过“改配置 -> 清缓存 -> 重新构建 -> 实测结果”的方式，真正把问题解决了。为什么现在就做这件事？因为如果当前阶段根本不需要那几种产物类型，却一直保留着，就会让以后每次编译都背着不必要的石头跑步。

除了代码和脚手架，今天我还做了一件面向“未来开发效率”的事情：在新仓根目录建立了 `AGENTS.md`。这个文件不是给最终用户看的，而是给以后在这个目录里继续干活的代理或开发者看的。我把今天已经形成的共识都写进去，比如：当前阶段只做基础准备、不能提前迁移业务；前端保留 Vite + React；字幕 sidecar 保留 Node；当前代理端口是 `3066`；本地绝对路径配置在 `config/local.paths.json`；Rust 宿主当前只保留 `rlib`，没有明确需要就不要恢复 `staticlib` 和 `cdylib`；常用命令是什么；每种改动最少该跑哪些验证。这个文件的意义，就像在工地门口贴了一张清晰的施工守则，后面不管谁来干活，都知道现在是在做什么、不该做什么。

现在回头看，今天这轮工作的真正成果，不是“已经开始迁移业务”，而是“把未来迁移这件事从模糊想法，变成了一个有清晰边界、有新仓、有脚手架、有验证、有本地说明、有技术决策记录的实际工程起点”。老项目那边暂时还不用受影响，它可以继续安心收束 theme 系统；新项目这边则已经有了自己的地基。等以后时机成熟，就可以在这个新仓里按我们今天定下的策略，一块一块、有秩序地把真正值得迁移的部分搬过来。

如果要把今天的工作讲给小朋友听，我会这样总结：我们今天没有急着把旧家的玩具全扔到新家去，而是先画好了搬家计划，决定哪些玩具先搬、哪些先不动；然后真的把新家的房间分好、门装好、电通好、水接好，还检查了灯会不会亮、风扇会不会转、厨房能不能打火。中间也遇到了麻烦，比如钥匙插错孔、工具没通电、房门没挂牌、搬家箱子太大，但最后都一个个解决掉了。这样等真正开始搬家具的时候，就不会手忙脚乱了。

不过今天的事情并没有在这里停下，后面我们又继续把一些关键决定想得更细，让这份计划不只是“一个大方向”，而是真正可以拿来施工的图纸。先聊到的是 `sharp`。因为前面我们已经在新仓里装好了 `sharp` 并跑通了检查，所以很自然地会问：那以后是不是就该把它直接换成 Rust 版本，才算“更先进”？这里我们把话讲得很实在：当前新仓里的 `sharp` 仍然是走 Node.js 这条路，它现在只承担一个任务，就是证明这个依赖能正常安装、能正常执行，并不等于缩略图链路已经决定永远这样做。更重要的是，我们再次确认了一件很容易被误解的事：未来“缩略图 Rust 化”真正的价值，不一定是找到一个名字听上去像“Rust 版 sharp”的东西，而是让缩略图整条流水线，包括读取源图、调度任务、缓存命中、预加载和写入缓存，都由 Rust 来负责。也就是说，好处主要来自整条运输链变顺了，而不是单独把刀片换成另一种材质就会神奇地切得飞快。

接着我们又专门把压缩包方案掰开揉碎地讲了一遍。因为之前说到“重 I/O 值得迁 Rust”时，压缩包其实是最核心的场景之一，但这件事不能只说“压缩包”三个字就完了，要看具体是哪些格式、在项目里怎么用。我们去对照了旧项目的实现，确认当前项目识别的压缩包格式主要是 `.zip`、`.rar`、`.7z`。其中最重要、最频繁的，是 `zip`。它不是靠某个黑盒库在读，而是项目自己在 Node 环境里读取 ZIP 的中央目录、算偏移、判断压缩方式，再按 `store` 或 `deflate` 去取内容。`rar` 和 `7z` 则是借助 `node-unrar-js`、`7z-wasm` 之类能力，再把结果归一化成更适合后续使用的内部 zip 形式。这一步像是我们终于把“仓库里有哪些箱子”这件事数清楚了，知道平时高频搬来搬去的是哪种箱子，哪些只是偶尔经过门口需要重新装箱的。

然后我们把问题问得更尖锐了一点：如果未来迁到 Rust，在“默认大量读取 zip、审核和编辑删除时还要保存 zip”这个场景里，到底能比当前 Node 方案好多少？这次结论比前面更明确了。因为当前项目里的 zip 读取虽然已经不算粗糙，但它依然运行在 Node 里，要经历 JS 对象、Buffer 分配、条目遍历和较松散的调度链路；而 Rust 非常适合做这种“高频读取 + 连续翻页 + 预加载 + 编辑后重写保存”的工作。所以我们形成的判断是：未来对 zip 主链路做 Rust 原生化，是非常值得的，而且这很可能会成为整个迁移里最能真正让人感受到收益的部分之一。尤其是在大型 zip 包的条目索引、连续翻页、预加载以及审核删除后重新保存这几个点上，Rust 有很大机会不仅更快，还更稳、更省内存。这不是一种夸张的口号，而是因为这类任务恰好是 Rust 擅长的“顺序流式处理 + 低开销调度 + 原生 I/O”场景。

但说到 `rar` 和 `7z`，情况就不同了。这里我们做出了一个非常实用的决定：如果 `rar` 和 `7z` 在项目里只是在“入库时做一次归一化”，那就没必要为了这一步去强行追求纯 Rust 方案。因为真正高频的日常查看、预加载、审核、保存主链路，未来都应该围绕 `zip` 来设计，`rar/7z` 更像是入库时的低频来客。既然它们只在门口出现一次，那最合理的做法不是为它们单独建一条昂贵又复杂的新高速公路，而是继续用成熟的外部工具把它们转成内部标准 zip，然后后面的所有流程都统一走 zip 主链路。我们甚至把这件事说得更直白了：当前项目既然已经有和 `7z` 相关的思路基础，那么未来在 Rust 中继续沿用 `7z.exe` 来做归一化，完全是合理而且推荐的。没有必要为了“纯 Rust”这四个字，去牺牲兼容性、稳定性和开发效率。换句话说，我们把“是不是纯 Rust”放到了“是不是更适合项目实际”之后。

这个决定其实非常关键，因为它让未来压缩包路线的主次彻底明确了：高频主战场是 `zip`，值得 Rust 原生深耕；`rar/7z` 是低频入库路径，适合继续用成熟外部工具归一化。这样一来，项目资源就不会被低频边缘路径分散掉。就像修路时先把城市主干道铺好，而不是先花大力气去修一年只走几次的小山路。

在这些方案讲清楚后，我们就反过来回头看新仓本身，看看当前初始化工作还缺什么。你先问了一个很有代表性的问题：现在这个仓库虽然已经能跑，但最初那份实施计划文档是不是应该跟着最新决定一起更新？这其实是非常好的提醒。因为如果讨论已经往前推进了，文档却还停在比较早期的版本，就像施工队已经改了图纸，但墙上挂着的还是旧图，后面的人会很容易走错。于是我没有只改一两句，而是把原来的初始化计划重新整理成了一份更完整的实施计划文档。里面不只是保留了最初“新仓 + monorepo + Tauri + React + 字幕 sidecar”这些大方向，还把后来新确认的内容全部补了进去，比如：保留前端 Web 技术栈的原因、字幕为什么保留 Node sidecar、压缩包路线为什么要把 `zip` 作为高频主链路、为什么 `rar/7z` 只在入库时归一化并优先继续沿用 `7z.exe`、为什么当前缩略图仍只在 Node 侧验证 `sharp`、为什么 Rust 宿主要暂时只保留 `rlib`。这样一来，`docs/archive/root-plans/migration-plan.md` 就从一份“初始化说明”升级成了一份真正可执行、可检查、可追踪的实施计划。

更重要的是，我没有只是把计划写漂亮，而是顺手把“当前到底已经完成了什么、还差什么”也直接写成了检查清单。这样以后再看文档时，就不是靠记忆想“我们是不是已经做过这个了”，而是能一眼看到哪些项已经打钩、哪些还没做。比如：新仓和 workspace 已经建好，`apps/desktop`、`apps/subtitle-sidecar`、`packages/contracts`、`src-tauri` 都已经存在；`React + Vite` 默认页面已经能构建；`Tauri` 宿主能启动；`rusqlite`、`sharp`、`ffmpeg`、`mpv` 的 smoke check 已经通过；但像 `zod`、`zustand`、`three` 还没接进前端，`tokio`、`zip`、`reqwest` 等还没接进 Rust，字幕 sidecar 的最小 ping/heartbeat 也还没做。这种清单看起来朴素，实际上非常有价值，因为它会让后续开发节奏更稳，避免重复劳动或者错把“想做的事”当成“已经做了的事”。

后来你又选择继续推进实施计划中的第一项，也就是把最初预留但还没真的建出来的 `crates/*` 骨架和 `.github/` 目录补齐。于是我又回到新仓，真正创建了 `crates` 目录，以及 `app-core`、`media-io`、`media-db`、`media-thumb`、`media-playback`、`shared-model` 这些子目录。这里我们特别克制，没有马上把它们变成真正的 Rust crate，也没有提前往里面塞业务代码。只是先把目录和每个目录的职责说明补好，像在一栋还没入住的楼里先挂好每个房间的门牌：这个房间以后放数据库，这个房间以后放重 I/O，这个房间以后放播放器控制。还顺便把 `.github/` 目录也建起来，给将来的 CI、Issue/PR 模板留位置。这个动作看起来简单，但它把后续模块拆分的格局先稳住了，避免以后临时起名、临时挪文件、临时决定边界，越改越乱。

再往后，我们终于做了一个对迁移很有象征意义的小动作：打通最小的 `desktop <-> tauri command` 示例。这个东西听起来像一串术语，但本质上很简单。它要证明的是：现在 React 前端不只是能在 Tauri 窗口里显示，而是真的能跟 Rust 宿主“说话”了。我们还专门用 Electron 项目做了类比：以前在 Electron 里，前端要调用后端能力，一般要经过 `window.mediaPlayerBackend`、`preload`、`ipcRenderer`、`ipcMain` 这一整串通道；到了 Tauri 里，未来这套桥接会简化成 `React -> invoke(command) -> Rust command -> 返回结果`。为了验证这个新通道已经通了，我没有做复杂能力，而是挑了最小的一个例子——调用 Rust 侧已经存在的 `greet` command。

具体实施时，我把 `apps/desktop/src/App.tsx` 从原来那个 Vite 默认的计数器页面，换成了一个更有意义的小面板：上面有一个输入框，你可以输入一个名字；旁边有一个按钮，点一下就会从前端通过 Tauri 的 `invoke` 去调用 Rust；Rust 返回一句问候，再在页面上显示出来。这个页面看上去很简单，但它的意义很像在新家的总电闸接好之后，第一次按下开关看到灯真正亮了。因为它告诉我们：现在不是“React 能跑”和“Rust 能跑”分别成立，而是“React 已经能真实调用 Rust 宿主能力”这件事成立了。后面无论是读取配置、打开文件、查询数据库、调起媒体资源，都会沿着这条链路往前扩展。

做完这个最小桥接示例之后，我也没忘记继续做验证。先重新跑 `npm run build:web`，确认前端不是只在开发环境勉强工作，而是真的能构建成功。然后再跑 `npm run check`，确保加了这个示例页面之后，原本已经通过的 `sharp`、`rusqlite`、`ffmpeg`、`mpv` 这些基础自检没有被破坏。结果都顺利通过。最后我还把“最小 `desktop <-> tauri command` 示例已完成”这件事同步更新回实施计划文档，让文档状态继续和实际仓库保持一致。这一步虽然看起来像文书工作，但实际上非常像工程中的“施工完一项就更新看板”，能让下一次接手的人立刻知道现状，而不是靠口口相传。

所以，如果把今天后半段新增的工作也一起算进去，今天做成的事就又多了一层。前半段我们解决的是“这条迁移路值不值得走、怎么走、工地怎么搭”；后半段我们解决的是“哪些地方必须进一步想清楚，哪些低频路径不要过度设计，文档怎么跟上真实决策，模块骨架怎么提前摆好，以及前端和 Rust 之间的第一条真正通信通道怎么打通”。这样一来，`C:\opencode\MediaPlayerNext` 就不再只是一个“能启动的新项目”，而是一个已经有清晰方向、有模块预留、有实施计划、有日志、有开发规则、还有最小前后端桥接样例的新工程基地。

如果继续用讲给小朋友听的方式来总结今天后半段的工作，那就是：我们不只是给新家通了水电，还开始给每个房间挂上名字，决定厨房以后放哪里、书房以后放哪里、仓库以后放哪里；还试着从客厅按了一个按钮，让楼下的电梯真的动了一次，证明这栋楼的线路不是画在纸上的，而是真的接通了。与此同时，我们也决定了一件很聪明的事：那些平时不怎么用、但偶尔会来的大箱子，不必为了它们专门建一套复杂机器，先用成熟工具把它们整理成统一大小的箱子再放进仓库就行。这样以后真正搬家的时候，大家就会轻松很多。
