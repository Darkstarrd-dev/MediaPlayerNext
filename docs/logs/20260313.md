# 2026-03-13 工作记录

## 今天主要在做什么

今天主要推进的是桌面端主题调试系统首轮落地。

如果用一句话概括，这件事是在解决“当前 UI 变量虽然已建立合同，但缺少可视化调试入口”的问题，目的是让 `1.0~2.4` 根级变量可以直接在新仓内调试、导入导出并快速回放。

## 为什么今天先做这件事

当前项目已经进入“布局先行、样式链重建、面板逐步接回”阶段。这个阶段继续堆业务页面会放大样式回归成本，所以先把主题调试链路立起来，能降低后续面板接回时的视觉回归风险。

这样安排的原因是：
- `3 大面板层` 已可复用，具备承载主题调试的 UI 骨架条件。
- `Header` 已是稳定入口，增加调试按钮不会破坏现有导入与设置流程。
- 当前只做根级 `1.0~2.4`，可以控制复杂度，避免提前进入子级细节爆炸。

## 今天推进了哪些关键点

### 1. Header 新增主题调试入口，并接入独立大面板层

这件事本身做了什么：在 `Header` 右侧新增“主题调试”按钮，点击后打开独立 overlay 大面板；并把它接入 `AppShell` 现有 overlay 互斥与 ESC 关闭链路。

它的重要性在于：主题调试成为固定入口，不再依赖临时页面或开发态硬编码。

它对后续的帮助是：后续新增主题分页时可沿用同一入口与同一骨架，不需要重复造壳。

### 2. 首轮主题调试面板只保留双分页

这一步解决的是：避免一次性迁入旧项目大体量 Theme Parameter 页面，先建立最小可用闭环。

具体落地为：
- 分页一：`参数导入导出`
- 分页二：`大容器层调试`

它说明目前项目已经从“只有变量合同”进入到了“有可操作调试面板”。

### 3. 调试范围固定为根级 1.0~2.4，不下探子级

另外补上了根级范围约束：
- `1.0` 背景层
- `2.0` 共享壳层
- `2.1` Header Root
- `2.2` Sidebar Root
- `2.3` Main Root
- `2.4` Metadata Root

这件事虽然看起来不大，但它的意义是：保持首轮成本可控，避免把变量层级细节与 UI 验收耦合到同一次迭代中。

### 4. 参数导入导出页补齐最小快照动作

这件事本身做了什么：支持导出到文本框、下载 JSON、复制 JSON、加载 JSON 文件、应用导入、清空文本框。

它的重要性在于：主题调试值可以保存、共享与回放，不再只能手工逐项重填。

它对后续的帮助是：后续可以把快照直接用于 E2E 前置状态准备与回归对比。

### 5. 2.0 布局项采用系数同源策略

这一步解决的是：`layout-padding / splitter-width` 与设置页滑杆的冲突风险。

处理方式是：主题调试面板里这两项继续走系数链路（`layoutGapScaleCoeff` / `splitterWidthScaleCoeff`），与设置页保持同源。

它说明目前项目已经明确“同一语义只保留一条运行时写入链路”。

### 6. 补齐 2.2~2.4 root slot 的样式消费

另外补上了 `Sidebar / Main / Metadata` 根容器对 `bg/border/shadow` slot 变量的消费入口。

这件事虽然是样式层改动，但意义是：主题调试面板里的 `2.2~2.4` 参数不再只改变量名而无视觉反馈。
