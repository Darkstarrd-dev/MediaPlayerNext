### 4. 明确当前阶段 Rust 质量验证是怎么做的
今天还顺手把一个很容易让人混淆的问题理顺了：在 Rust 开发里，当前这阶段的质量验证，并不是靠单一命令完成，而是分层进行的。

这一步解决的是：很多人熟悉前端开发，但不一定熟悉 Rust 的工程流程，容易把 `cargo fmt`、`cargo check`、`cargo test` 都看成差不多的事情。实际上它们分别承担的是格式检查、编译级验证、测试验证和冒烟验证，不是一回事。

目前我们已经明确，当前阶段主要依靠四层验证：
- `cargo fmt`：检查代码格式是否统一，更接近前端里的格式化检查。
- `cargo clippy`：做静态规则检查，更接近前端里的 `eslint`。
- `cargo check`：做编译级检查，确认整个工作区在依赖锁定后能通过编译。
- `cargo test`：执行 Rust 测试，覆盖单元测试、最小集成验证等内容。
- CLI harness / runtime smoke：做最小可运行性检查，作用上接近 Electron 里的冒烟测试。

它说明目前项目已经不是“写完代码看能不能跑”那种松散方式，而是在逐步形成一套有层次的质量门禁。

为了让非 Rust 背景的人更容易理解，目前可以先用下面这张对照表来建立直觉：

| Rust 命令 | 当前作用 | 可类比的前端命令 |
|---|---|---|
| `cargo fmt` | 检查代码格式是否统一 | `prettier --check` |
| `cargo clippy` | 静态规则检查与坏味道提示 | `eslint` |
| `cargo check` | 编译级验证，不产出最终发布包 | `tsc --noEmit` |
| `cargo build` | 真正构建产物 | `npm build` |
| `cargo test` | 运行测试 | `vitest` |
| CLI / smoke check | 检查最小链路能否运行 | Electron 冒烟测试 |

这里也形成了一个比较重要的判断：
- `cargo fmt` 不能简单理解成 `eslint`，它更像格式化检查。
- `cargo check` 也不能直接等于 `npm build`，它更像“先确认能不能编过”。
- 真正更接近 `eslint` 的是 `cargo clippy`。
- 真正更接近 `npm build` 的是 `cargo build`。

这件事对后续的帮助是：后面进入数据库、扫描、zip 等真实能力开发时，大家会更清楚每一层验证是在防什么问题，也更容易理解为什么要同时保留格式、静态检查、测试和冒烟这几类质量动作。

它对后续的帮助是：后面做任务中心、扫描中断恢复、UI 状态展示时，不需要再回头重新设计“失败怎么表示、恢复从哪进入”这两个最基础的问题。

今天又补了一块偏“质量治理”的内容：把扫描验证本身写成了可执行计划，而不是停留在“以后记得测一下”。

今天把这件事写清楚之后，扫描验证就不再只是开发者脑中的经验，而是变成了后续必须执行、必须记录、并且能据此调整设计的正式环节。

它对后续的帮助是：后面做 `medium-fixture` 扫描验证、本地真实目录验证，以及进入 `B4` 前的阶段回归时，都已经有统一口径，不需要每次临时决定“拿什么测、测完记什么、什么结果算有问题”。

### 11. 先把三层扫描数据集的占位骨架真正生成出来
今天还把“数据集要求已经写进文档，但仓库里还没有足够多真实样本”这个落差继续往前推进了一步。

这件事本身做了什么：新增了扫描占位数据生成脚本，可以一次性生成三层目录：仓库内的 `small-fixture/generated-placeholder`、`medium-fixture/generated-placeholder`，以及本机 `data/scan-validation/local-real-dir-mock`。这些数据不是纯文件名，而是真实存在的占位文件；图片、音频、zip/cbz 都会生成真实可读样本，视频在本机 `ffmpeg` 可用时也会生成真实最小文件。

后面又进一步收了一层边界：`small-fixture` 仍保留仓库内小样本基线，`medium-fixture/generated-placeholder` 与本地 mock 目录则按本地生成物处理，不进入 Git，避免仓库因为中等规模扫描样本持续膨胀。

随后又把 `medium-fixture` 往前推进了一步：如果 `generated-placeholder/realdata` 下已经准备了真实样本池，脚本会优先从里面按类型随机抽样，把对应类型的占位文件复制到 `generated-placeholder/scan-root`；这样既能保留原先规划好的路径分布和目录骨架，也避免把样本池本身误扫进验证结果里，从而尽快把中等规模扫描验证从“全占位”推进到“混合真实文件”。

后面又把这条规则进一步统一到了大目录 mock：`realdata` 现在被视为一次性样本输入，而不是最终目录的一部分。也就是说，无论是 `medium-fixture` 还是 `local-real-dir-mock`，脚本都会先用 `realdata` 做随机替换，再把它清理掉，只保留最终用于扫描的目录结构。这一步的意义是把“样本池”和“扫描根”明确分离，避免真实样本池被误计入统计，也避免本地 mock 目录长期混着两套内容。

后面又暴露出一个更关键的问题：如果脚本默认每次都重建目录，就会把已经替换好的真实文件重新覆盖回占位文件。这个行为对当前阶段是错误的，因此后续已经调整为“默认保留现有目录、只有显式 `--force` 才重建”的安全模式，避免再次误覆盖本地真实测试数据。

随后又把整个数据集工作流收束成了更稳的一版：不再把“真实文件填充”和“日常测试复制”混在一个脚本里，而是拆成两步。第一步，用一次性脚本把 `realdatasmall` 和 `realdata` 的真实文件填充进 `small`、`medium`、`local` 三个基线目录；第二步，日常测试时统一从这三个基线目录复制到 `data/scan-validation/runs/` 下的临时目录，测试结束后再删除。这样做的意义是把“珍贵样本基线”和“可破坏的测试副本”彻底分开，避免每轮测试都去碰真实样本目录。

### 12. 开始第一轮真实样本扫描验证记录
今天还把“真实样本已经就位”这件事继续推进成了真正的验证记录，而不是只停留在样本准备阶段。

这件事本身做了什么：先用一次性脚本把 `realdatasmall` 和 `realdata` 填充到 `small`、`medium`、`local` 三个基线目录，再创建 `data/scan-validation/runs/` 下的临时测试副本，对三套目录分别执行首扫、无变更重扫、删除加新增后的重扫，以及额外的失败/恢复入口验证，并把结果写成了正式记录。

它的重要性在于：项目现在第一次不是“理论上支持真实样本验证”，而是已经把真实文件基线、临时运行副本和实际扫描结果打通了。这样后续做 `B4` 时，就能直接在真实样本基础上验证 zip 索引与扫描链路是否冲突，而不是回到只靠占位文件推测行为。

它对后续的帮助是：从现在开始，扫描验证已经有了可重复执行的工作流，也有了第一版真实样本基线记录。后面无论继续补 `B3` 收尾，还是切入 `B4`，都可以直接复用这套目录和记录方式继续做回归。

### 13. 在 local 大目录上补做更大变更场景验证
今天还继续把扫描验证往更接近真实使用的方向推进了一步：不只验证“删一个、加一个”的最小场景，而是在 `local-real-dir-mock` 的临时副本上补做了一轮更大规模的变更测试。

这件事本身做了什么：在 `data/scan-validation/runs/` 下的新副本里，一次性删除了 10 个图片文件、新增了 6 个图片副本，并修改了 5 个已有媒体文件的时间戳，然后重新执行扫描、统计和 resume 验证。

它的重要性在于：这比最小场景更能说明当前扫描模型在“真实目录发生一批变化”时，能不能稳定给出新增、未变化、tombstone 和活动文件统计，而不是只在非常温和的单文件场景下成立。

它对后续的帮助是：这轮结果已经可以作为 `B3` 收尾的一部分依据。因为它说明当前增量扫描的最小语义在更大变更量下仍然成立；同时也把 `resume` 仍然只是整轮重跑、在大目录下耗时偏高这个问题更明确地暴露出来，为后面是否继续补恢复策略提供了更具体的证据。

这件事本身做了什么：把 `crates/media-playback` 变成真实 crate，拆出 `ffprobe`、`ffmpeg`、`mpv`、`session` 四个模块；其中 `ffprobe` 负责 JSON 输出解析，`ffmpeg` 负责首帧抽帧参数和 progress 解析，`mpv` 负责最小启动参数，`session` 负责把首版播放会话持久化到磁盘并支持 `open/status/pause/seek/stop` 这一层最小控制语义。

应用层与宿主层也同步接上了：`app-core` 新增了 `playback` 模块，可以按 `asset_id` 做 probe 并回填 `media_assets` 的基础元数据，也可以打开和查询播放会话；`src-tauri` 则新增了 `media://asset/<asset_id>` 与 `archive://entry/<archive_entry_id>` 两条 custom protocol，并把 `ffprobe` 加进了 runtime smoke。这样后续前端要拿缩略图、媒体文件、归档 entry 时，都已经有明确的协议入口，不需要再通过 command 运大字节。

这里最关键的变化不是“支持了某个命令”，而是后续 UI 可消费的三类输入面终于都开始成形了：`thumb://`、`media://`、`archive://`。从这个节点开始，控制面和字节面已经比较清晰地分离开，后面继续做播放器或归档浏览时，协议边界不会再漂移。

今天还把 contracts、README、runtime smoke、fixture 和 validation 文档一起补了。也就是说，`B7` 并不是只在 Rust 里多了几个模块，而是连命令口径、协议口径、样本约束和验证记录都一起补到了第一轮可交接状态。

需要明确的一点是：当前 `mpv` 还没有接真正的 IPC 控制，`ffmpeg` 也还没做真实视频 benchmark；这些都属于后续增强，而不是当前进入 `B8` 前的阻塞项。就现阶段目标来说，`B7` 首版已经足够闭合。

它对后续的帮助是：下一步可以直接进入 `B8` 的 subtitle sidecar 宿主协议，把整个“后端主链路与宿主协议”阶段继续往前推进，而不需要再回头补播放侧的最小协议与会话地基。

## 今天遇到的问题

### 1. Windows 下 Rust 校验不能直接按普通方式跑通
今天遇到的问题是：Rust 工作区在普通环境下执行完整检查时，SQLite 的 bundled 编译链路还是会受 Windows/MSVC 环境影响，直接跑会出现头文件路径不完整的问题。

它带来的影响是：如果忽略这件事，表面上看代码已经写好了，但真正到需要编译、测试或 CI 落地时，可能会在本地环境与工具链交界处卡住。

最后的处理方式是：继续使用仓库里已有的 `run-cargo-with-msvc.cmd` 包装脚本，通过 Visual Studio 开发者命令环境来执行 `clippy`、`test`、CLI harness 等检查。

这件事说明后续需要特别注意：在 Windows 桌面场景下，Rust 代码的“能写出来”和“能稳定构建验证”是两件事，工具链环境仍然要被当成正式工程条件来管理。

### 2. 工作区引入后，原有细节约束开始暴露出来
今天还发现：一旦把占位目录真正接入 workspace，很多以前不会立刻暴露的问题就会集中出现，比如 TypeScript 在 `NodeNext` 模式下要求显式导入扩展名，Rust 的 `clippy` 也会对字符串格式写法提出更严格要求。

目前的结论是：这不是坏事，反而说明仓库正在从“能放文件”进入“要按工程标准运行”的阶段。越早让这些约束暴露出来，后面就越不容易积累隐性技术债。

### 3. B2 开始后，数据库层的工程问题也同步暴露出来
今天还发现：一旦真正开始做数据库层，问题不再只是“代码风格”或“模块结构”，而是开始涉及迁移重复执行、Windows 下的编译环境、repository 接口命名冲突、测试 fixture 升级这些更接近真实工程的问题。

目前的结论是：这反而是一个好信号。因为它说明项目已经不再只是“搭脚手架”，而是进入了会真实碰到数据一致性和工程边界的阶段。

这类问题最后的处理方式是：通过补 migration runner、补 `N-1 -> N` 升级测试、补批量写入测试和事务回滚测试，把风险尽量前移，而不是等扫描或 UI 接入时再发现底层不稳。

### 4. B3 开始后，链路问题开始从“结构问题”变成“真实流程问题”
今天还发现：一旦开始做扫描闭环，问题就不再只是模块有没有、接口怎么叫，而是变成了真实流程层面的细节，例如扫描结果是不是被正确过滤、CLI 路径是不是能稳定复用、统计命令在第一次与第二次执行时表现是否一致、工作区新增依赖后锁文件是否需要同步更新。

目前的结论是：这同样不是坏事。因为这说明项目已经开始进入“真正跑流程”的阶段，而不是只在写架构骨架。

最后的处理方式是：一边补最小 fixture 和 CLI smoke，一边用数据库实际内容去核对结果，确保 `scan add-library -> scan run -> scan stats` 这一条链路不是“理论成立”，而是“实际已经能跑”。

### 5. 进入 B3 后，验证方式也开始从“单元为主”转向“流程为主”
今天还发现：到了扫描阶段，单纯的单元测试已经不够说明问题了，因为很多风险不在一行函数里，而是在“命令怎么串起来、数据库有没有真的写进去、第二次执行结果会不会变”这类流程行为上。

目前的结论是：B3 之后的验证必须同时保留两层：
- 代码层：继续用 `cargo test`、`cargo check`、`clippy` 保证逻辑和结构不坏。
- 流程层：用 CLI smoke、fixture 目录、真实数据库结果核对，保证扫描主链路是真的跑起来。

这件事说明：越往后做，验证的重点会越来越偏向“系统行为”，而不是只看某个模块能不能编译。

### 6. B3 深化后，接口命名冲突开始变成真实治理问题
今天还遇到一个很典型的工程问题：随着 repository 能力变多，像 `get` 这种名字在不同接口上开始出现重名，测试里如果直接写方法调用就会产生歧义。

目前的结论是：这类问题虽然小，但很值得尽早暴露。因为它说明仓库已经从“只有少量接口”进入“接口逐渐增多、边界开始真正发挥作用”的阶段。

最后的处理方式是：在需要的地方显式按 trait 指定调用归属，保证测试和实现都能清楚表达“当前在操作哪个 repository 能力”。这类细节现在修掉，后面接口继续扩展时会更稳。

### 7. 文档如果不随实现一起更新，很快就会失去指导意义
今天还进一步确认了一件事：到了这个阶段，计划文档不是一次写完就放着不管的材料，而是要随着 B1、B2、B3 的真实进展持续修正。

目前的结论是：如果实施计划不写完成情况，后面再回头看时，很难快速分清“这个阶段是完全没做、只做了一部分，还是已经完成但还没切下个阶段”。

最后的处理方式是：把计划文档改成“既能指导后续，也能反映当前状态”的形式，这样它才真正能作为开发节奏和阶段判断的依据。

### 8. 数据集要求如果写得太泛，后面会直接影响扫描模型判断
今天还确认了一点：扫描验证的数据集要求不能只写“多准备一些文件”，而必须明确写出媒体类型、真实文件要求和路径编码要求。

目前的结论是：如果不提前把这些要求写清楚，后面最容易出现三类偏差：
- 只拿图片和 zip 去验证，结果音频和视频分类从一开始就缺少样本约束。
- 只拿文件名和后缀像真的占位文件去验证，结果对真实媒体分布的适配能力被高估。
- 只在英文路径下验证，结果中文、日文、带空格路径进入真实使用环境后才暴露问题。

最后的处理方式是：把 `small-fixture`、`medium-fixture`、本地真实目录三层数据集的要求全部写细，并且把中、英、日、空格路径都纳入约束。这样后面做扫描验证时，才能真正覆盖项目最终会面对的文件分布。

## 今天形成了哪些判断
- 已经确认：`B1` 的核心不是做功能，而是把后端开发地基真正搭起来。
- 已经确认：`B2` 的核心不是“先把数据库做复杂”，而是先把 schema、migration、repository 这三层稳定下来。
- 已经确认：`B3` 的首批重点不是一次做完全部扫描能力，而是先把“发现文件 -> 分类 -> 写库 -> 统计”这条最小链路跑通。
- 已经确认：`B3` 的第二批重点是把重扫、未变化跳过、`exists=false` 这些语义补起来，否则后面所有“增量”能力都会失真。
- 已经确认：`B3` 的第三批重点是把失败态、resume 入口和快照读取这些“运维语义”补起来，否则任务系统后面会缺观察面。
- 已经确认：实施计划文档必须同步记录完成情况，否则到了 `B3/B4` 交界处会很难判断当前真实阶段。
- 已经确认：扫描验证计划和数据集要求必须写进文档，否则真实负载验证很容易被拖到太后面。
- 已经确认：扫描数据集从现在开始就要覆盖图片、音频、视频、归档，以及中文、英文、日文、空格路径。
- 已经确认：在真实数据逐步到位前，先用脚本生成合规占位文件是合理的，但后续仍要用同类真实文件替换，不能把占位样本当成最终验证结论。
- 暂时不做：缩略图主链路、zip 浏览最终接线、复杂 `src-tauri` 桥接。
- 优先级靠后：`media-thumb`、`media-playback`、sidecar 协议的真实实现。
- 原因是：如果先跳去做这些重能力，而数据模型、contracts、workspace、CLI 骨架、数据库地基和扫描主链路都还没稳定，后面很容易推倒重来。
